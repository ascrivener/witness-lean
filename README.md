# witness-lean

A [witness](https://github.com/ascrivener/witness) check for Lean 4 proofs: bounties for theorems,
paid to whoever proves them, checked on JAM by an independent Lean kernel,
[nanoda](vendor/nanoda/VENDORED.md).

It has proved "there are infinitely many primes" on a local PolkaJam testnet, from Mathlib (see
[Numbers](#numbers)).

## How it works

Every blob the check receives is a *node*: one declaration with its own tables of names, levels and
expressions, naming the nodes it uses by hash ([format](tools/lean/node_format.md)). A theorem's
node is its statement; its proof is separate. So a node means the same thing wherever it's
loaded, and checking a declaration needs only the statements it uses, not a whole export.

- **Attest mode** type-checks a batch of nodes (the subjects), each theorem with its proof (the
  witness), trusting attested nodes for everything the batch imports. Params are empty. A library
  is attested this way in batches, by dependency depth, each once, by anyone.
- **Reveal mode** takes params `goal`, the hash of the bounty's theorem
  statement node, say `theorem goal : Goal`. The poster can hash it without a proof, since a
  statement node doesn't hold one. The witness is the solver's nodes and proofs; they must prove
  the goal node, trusting attested nodes for the rest.
- Every node must import every constant it mentions, no name may be declared twice, and the
  kernel's special names may only come from pinned nodes. Otherwise a node could declare its own
  `Nat.add` (or `axiom propext : False`) and the kernel would trust it by name. The *pins*, the
  hashes of the nodes allowed to declare the names the kernel treats specially (`Nat`, `Nat.add`
  and the other operations it computes with natively, and the permitted axioms), are built into
  the check for its Lean toolchain ([`check/pins.txt`](check/pins.txt), made by
  `tools/lean/lean_pins.py`): nodes are canonical, so they hash the same in any export on that
  toolchain. The check's hash fixes them, so every attestation by one check was made under the
  same pins.
- Only `propext`, `Classical.choice` and `Quot.sound` may appear as axioms, so no `sorry`.

A bounty goes like this (`scripts/lean-e2e.sh` runs it end to end):

1. The library is converted to nodes (`tools/lean/lean_nodes.py`), planned into batches by
   dependency depth (`lean_plan.py`), and attested batch by batch. Batches of one depth are
   independent, so they can be attested at once.
2. The poster hashes the statement node of `theorem goal : Goal` and posts a bounty with params
   `goal`. The bounty cites one attested node (its `Goal`, say): witness lets a reveal trust
   attested nodes only if its bounty cites one.
3. The solver exports their proof, commits, and reveals their theorem and its proof (and any
   lemmas of their own), trusting the attested nodes they need.

## Layout

```
check/                Lean check (crate lean-check), with test fixtures in check/testdata
vendor/nanoda/        nanoda_lib, a Lean 4 kernel checker, ported to no_std (VENDORED.md)
tools/lean/           lean4export to nodes, batch planning, packing witnesses; measurements
tools/lean-host/      runs the check natively and times it, for sizing batches
scripts/lean-e2e.sh   a Lean bounty end to end on a local PolkaJam testnet
```

`witness-check` and `witness-types` come from witness by git, pinned in `Cargo.toml`. witness is
private for now, so CI needs a `WITNESS_READ_TOKEN` secret that can read it.

## Build and test

```bash
cargo test                        # the check, on fixtures: honest proofs and attacks
cargo jam-build --out-dir out     # out/lean-check.jam
```

The fixtures in `check/testdata` (regenerated by its `make.sh`, from the Lean project beside it)
are node packs, and cover honest proofs and the attacks: a different theorem, a `def`, an extra
axiom, `sorry`, a redefinition, a statement edited after the fact, unpinned built-ins, nodes
missing an import or mentioning what they don't import, and theorems without proofs.

End to end, with a witness checkout for the service and its CLI, and a PolkaJam testnet (see
witness's README for running one in a container, and with the full spec's refine gas):

```bash
WITNESS_DIR=../witness LEAN4EXPORT=../lean4export/.lake/build/bin/lean4export \
  POLKAJAM_DIR=... scripts/lean-e2e.sh            # gcd a b = gcd b a, over Lean core
... scripts/lean-e2e.sh primes                    # infinitely many primes, over Mathlib
```

`primes` fetches Mathlib's build from its cache (`lake exe cache get`), which needs
`cache.mathlib.org`.

### All of Mathlib

`scripts/mathlib-full.sh RUN_DIR` attests all of Mathlib in witness-sim, start to finish:
1. export and convert;
2. profile;
3. lay out, with each heavy op near the limit run in PolkaVM;
4. check every item natively;
5. attest.

Run it again after any stop: each step is skipped once done, and attesting resumes from the
simulated chain. It takes many hours and over 40 GB, so run it on a machine of its own, detached:

```bash
GITHUB_TOKEN=... bash scripts/vm-setup.sh   # a fresh Ubuntu VM: toolchains, both repos, lean4export, Mathlib's cache
tmux new -d -s mathlib "LEAN4EXPORT=~/jam/lean4export/.lake/build/bin/lean4export \
  ~/jam/witness-lean/scripts/mathlib-full.sh ~/mathlib-run"
tail -f ~/mathlib-run/run.log
```

`NAMES="A B"` exports only those declarations' closures, for a quick test.

## Numbers

Each attestation and the reveal must fit one refine. `tools/lean-host` runs the check natively
and times it. What a native millisecond costs in PolkaJam v0.1.29's gas depends on the machine
(about 29 M on one, 77 M on an M3), so `scripts/lean-e2e.sh` measures it first
(`tools/lean/gas_per_ms.py`) and budgets batches in gas. With `WITNESS_SIM=1` it runs the whole
flow against witness's simulator, which charges checks the gas PolkaJam does.

**gcd a b = gcd b a** (Lean core): 437 nodes in 33 batches over 33 depths. The heaviest
attestation uses 1.9×10⁸ gas, so it fits PolkaJam's tiny 10⁹ limit. It runs end to end on a local
PolkaJam v0.1.29 testnet with every blob carried as an extrinsic, so the chain holds only records.

**There are infinitely many primes** (`Nat.exists_infinite_primes`, Mathlib): 2,942 nodes
(1.8 MB of statements, 2.3 MB of proofs) in 112 batches over 73 depths, then the reveal.

| | Content-addressed | The positional format before it |
|---|---|---|
| Attestations | 112 batches, 73 rounds | 66 layers, one after another |
| Heaviest attestation | 1.25×10⁹ gas | 1.9×10⁹ gas |
| Median attestation | 2.9×10⁸ gas | 8×10⁸ gas |
| Reveal | 7.8×10⁷ gas | 1.1×10⁹ gas |

The reveal loads only the 220 statements the theorem needs. The heaviest batch trusts 796 nodes
(412 KB) from 76 earlier batches. Batches of one depth are independent, so with enough cores the
library attests in 73 rounds.

**x⁴ + y⁴ ≠ z⁴** (`fermatLastTheoremFour`, Mathlib), which the positional format couldn't fit at
all (its last layers alone would parse 4.6 MB): 7,579 nodes (5.5 MB of statements, 7.7 MB of
proofs) in 269 batches over 90 depths. The heaviest attestation uses 2.6×10⁹ gas, the median
4.7×10⁸, and the reveal 2.6×10⁸; 1.4×10¹¹ in all. Against witness's simulator the whole flow
takes under three minutes.

**The fundamental theorem of algebra** (`Complex.exists_root`, Mathlib): 46,201 nodes (52 MB of
statements, 81 MB of proofs) in 2,584 batches over 294 depths. A batch trusts only the nodes the
kernel touches while checking it (traced natively by `lean-host trace`), not their import
closure: that cuts trusted nodes 4.5-fold, to at most 1,040 per batch and 347 cited batches per
op. The median attestation uses 4.7×10⁸ gas, as for FLT, and 99% use under 1.8×10⁹. Against the
simulator, 2,185 batches attest; then one lemma, `iteratedFDerivWithin_succ_apply_right`, needs
more gas to check than a refine has (about 6.5×10⁹), and everything downstream waits on it.

**All of Mathlib**: 717,116 nodes, laid out by `tools/lean/mathlib_work.py` as 51,090 batches,
plus 46,446 ops for the 966 declarations too heavy for one refine. Those are split into judgments:
kernel cache entries attested in pieces that cite each other, then the declaration's own check,
seeded with them ([docs/design/heavy-declarations.md](docs/design/heavy-declarations.md); why it's
sound: [docs/design/judgment-soundness.md](docs/design/judgment-soundness.md)). Every one of the
97,536 passes checked natively; `scripts/mathlib-sim.sh` attests them in witness-sim, heavy ops
included, at about 1.5 a second on an 8-core laptop.

## Limits and next steps

- **Blobs travel with the ops, as extrinsics.** Every attest and reveal carries the check, its
  batch's nodes and the nodes it trusts (each with a Merkle path into its attestation), so the
  chain holds only records: no node is stored on chain. A package carries at most about 13.8 MB;
  Mathlib's batches trust at most about 3 MB. A batch's proofs, the check's witness, travel in the
  op up to witness's 64 KiB `MAX_WITNESS_LEN`, or as an extrinsic of their own (witness's CLI does
  that for any over 1 KiB); `lean_batches.py` still puts more than 60 KB among the subjects.
- **Built-ins are trusted by name in the kernel.** nanoda, like Lean's kernel, computes `Nat.add`
  and friends natively and permits axioms by name, so the check pins the nodes allowed to declare
  them, built in for its Lean toolchain (see How it works). A new toolchain needs a new check.
- **A heavy declaration costs several times its check.** 966 of Mathlib's declarations need more
  than a refine; split into judgments, the ones measured cost 3.4 to 5.5× their whole check, one
  16× (mostly rebuilding the terms of the entries each op seeds), and the heaviest takes 254
  rounds. That's most of Mathlib's gas.
- **Next:** the open questions in [docs/design/heavy-declarations.md](docs/design/heavy-declarations.md)
  (the overhead and latency of splitting, literal dependencies in the converter), a review of the
  judgment soundness argument by a kernel author, and Mathlib on a real testnet.
